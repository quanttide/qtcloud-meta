# 元本体：工具的自我建模

`examples/ontology/category.yaml` 描述的不是业务，是**工具自己所在的范畴**：`src/category/within.rs` 里的类型作概念（`OntologyDef`、`Report`、`LawGroup`……），类型之间的关系作边（`HasConcepts`、`HasLoaded`、`HasAnalyzed`……），报告必须具备的段落作公理（`ax-report-has-loaded`、`ax-report-has-analyzed`）。

## 定性

**它不是产品功能，是一次自食其力（dogfooding）——工具用自己的方法描述自己。**

不对外：不做成 CLI 功能，不给用户看 `category within category` 的报告。

## 为什么值得做

往外说，它证明三件事：

1. **输入模型够通用。** 没改一行代码，加一份 YAML 就能分析一个新范畴——客户可以定义自己的范畴，工具不硬编码。
2. **工具吃自己的狗粮。** 它分析业务本体用的那套方法，同样能分析它自己。可信度不是靠说的，是靠跑出来的。
3. **它是范畴间的预演。** 工具要跨范畴走，首先得能描述自己所在的范畴——`category.yaml` 里的概念与关系，正是范畴间那三张表要用的形状。**这条最实在**：给工具建模不是为了自举，是为了让它先能描述「自己」这个范畴，然后才谈得上跨到别的范畴去。

## 怎么下

| 层面 | 下法 |
| :-- | :-- |
| 产品 | 不做成 CLI 功能，不给用户看它的报告 |
| 工程 | 定位为**活的架构文档 + 回归测试**，进 CI |
| 向前 | `category.yaml` 演化成范畴间三张表的 schema 草稿 |

**关键在第二行。** 元本体如果只跑一次、看一眼，就是装饰品。要让它成为资产，得让它**能捕捉不同步**——改了代码、没改本体，测试要能红出来。那才是活文档，否则就是死注释。

落地就一件事：`tests/meta_ontology.rs`。它做两件检查：

- **对齐**：本体里声明的每个概念，都要能在 `src/category/within.rs` 里找到同名类型——改名、删类型却没改本体，这里红。
- **快照**：报告的关键数字（对象、声明态射、恒等、各公理组、派生）与写死的期望值一致——合法变更也要在这里留痕，红了就说明本体该跟着更新。

## 边界

**它是预演，不是交付。** 等范畴间真正实现，`category.yaml` 会被那三张表取代或吸收——那时建模的主体从「工具的结构」变成「范畴之间的映射」，元本体完成过渡使命。

## 一句话

给工具建模，下的定性是：**一次自食其力，产出是一份活文档和一个回归测试，顺带预演了范畴间的数据模型。不对外，对内，且明确它是过渡，不是终点。**
