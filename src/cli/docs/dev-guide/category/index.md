结论：一个 CLI，两个子命令

不是两个独立命令，也不是一个合并命令。是一个命令带 within / between 两个子命令。

```
qtcloud-meta category within  <范畴>
qtcloud-meta category between <源范畴> <目标范畴>
```

为什么是一个 CLI

1. 心智模型是同一个。 用户想的是「对范畴做分析」——有时是内部，有时是跨范畴。就像 git diff 和 git log：不同操作，都属于 git。拆成两个命令，用户得先知道「我这次要的是哪个命令」，多一层认知负担。

2. 表和报告约定共享。 within 用 category 表读承诺，between 也用 category 表；两者都输出报告给 LLM，都遵循「CLI 出事实，LLM 做判断」。这些约定集中在一个命令里维护，改一处两边同步。拆开就要维护两份。

3. 代码已经这样组织了。 两个文件都在 src/cli/examples/category/ 下，都是 pub fn run()，没有 main。这个结构本身就说明它们是同一个父模块的兄弟——一个 category 命令调度两者，是最自然的接法。

4. 可发现性。 一个 —help 能同时列出 within 和 between，用户一眼知道「范畴分析有两种」。两个独立命令，用户得先知道有第二个存在。

为什么不是一个合并命令

如果做成 category analyze <源> [目标]——给了目标就走 between，没给就走 within——听起来省事，实际会出问题：

 within between
输入 一个范畴 两个范畴
步骤 装载 → 分析 → 返回 选定 → 映射 → 冲突 → 缺失 → 结论
数学 已上场 还没上场
0 的含义 有的验过、有的空白、有的不可能 全是「还没做」

步骤数不同、数学成熟度不同、0 的含义不同。 合并成一个命令，报告里就分不清「结构公理 0 条」和「映射规则缺失」是同一类事还是不同类事。这正是前面反复强调的——要分清「没做」和「不可能」，就不能把它们混进一个出口。

为什么不是两个独立命令

两个独立二进制文件（within 和 between）只在一种情况下合理：受众完全不同、依赖完全不同、发布节奏完全不同。

这三个在现状里都不成立：

· 受众相同：都是「拿报告的一侧」
· 位置相同：同一个仓库、同一个目录
· 报告格式相同：都是给 LLM 的事实清单

拆成两个独立命令，只会带来重复代码、重复文档、版本不同步。唯一的代价——within 依赖 pr4xis、between 暂时不依赖——用 Cargo 的 feature flag 或普通依赖管理就能解决，不值得为它拆程序。

怎么设计

```
qtcloud-meta category within  <范畴>
qtcloud-meta category between <源范畴> <目标范畴>
```

上层 category 命令只做三件事：

1. 解析子命令
2. 调 within::run() 或 between::run()
3. 统一报告出口（比如加统一前缀、统一输出格式）

within.rs / between.rs 保持现在的 pub fn run() 不动。父模块负责调度和报告收口——这也顺便解决了之前提的「两份报告一级标题可能重名」问题：标题统一在父模块加前缀，子模块只管内容。

一句话记法

一个工具，两个子命令。
因为它们是同一件事的两种模式，共享表和报告约定；
但不能合成一个命令，因为「不可能」和「还没做」必须分开报。


两者的输入输出形状不一样：within 吃一个范畴、吐模型状态；between 吃一条路径、吐流程轨迹。分开说。

within

输入

项 现状（代码） 理想（CLI）
范畴 硬编码在 pr4xis::ontology! 宏里 qtcloud-meta category within <范畴>
本体 宏里声明 concepts / edges 按范畴标识读本体定义
业务规则 宏里没有 axioms: 读该范畴的 axioms: 子句

代码里 run() 无参——它只认 Media 这一个硬编码本体。理想形态下，输入是一个范畴标识，工具据此去读该范畴的本体、关系、标签、领域公理。

输出

run() 打印报告到 stdout，数据结构上分两块：

Loaded（装载结果）

· objects：对象列表（如 Content、Account、Material）
· morphisms：态射列表（含恒等）
· labels：对象的标签对

Analyzed（分析结果）

· groups：三组公理的校验结果（哪组、几条、几条过、失败原文）
· composable_pairs：可复合的态射对数
· derived：派生关系列表

报告文本分四段：装载、分析、关系清单、给后续分析的结论，末尾一条恒等见证。

一句话：输入一个范畴，输出这个范畴的模型状态——对象、态射、公理通过情况、派生关系。

between

输入

walk() 的参数就是完整输入：

参数 含义 现状
from 源范畴名 硬编码「实体导向」
to 目标范畴名 硬编码「流程导向」
assertions 要翻译的断言 硬编码 [”内容“, ”素材“]
categories category 表 硬编码一行
mappings category_mapping 表 硬编码一行
conflicts conflict 表 硬编码空

理想 CLI 是 qtcloud-meta category between <源范畴> <目标范畴>。注意：命令只给两个范畴，assertions 从哪来——这是输入里最没定的一项。现状是硬编码，理想上应该由源范畴的本体读出、或用户指定、或上层任务带入。这一点文档里还没定。

输出

walk() 返回 Report，run() 打印到 stdout：

字段 含义
steps 走到哪几步（1 选定 / 2 映射 / 3 冲突 / 4 缺失 / 5 结论）
conclusion 翻译结果对：源概念 → 目标概念
pending 挂起的 change_request，没有则为 None

报告文本是步骤列表 + 结论 + 挂起项。

一句话：输入一条路径（源、目标、要翻的断言、三张表），输出这次走查的流程轨迹——走到哪、翻出什么、有没有停下等人填。

对照

 within between
输入 一个范畴 一条路径（源 + 目标）
输入核心 本体定义 三张表 + 待翻断言
输出 模型状态 流程轨迹
输出数据 对象、态射、公理结果、派生 步骤、结论对、挂起项
输出性质 结构化（模型长什么样） 过程化（走到了哪）
遇到 0 「不该有 / 没做 / 不可能」三态 全是「还没做」
依赖数学 是 还没

关键差异在最后一列：within 的输出是模型快照，between 的输出是过程记录。 一个回答「这套模型现在什么状态」，一个回答「这条翻译路走到哪了」。

一个要留意的地方

between 的 assertions 输入没有自然来源。within 的输入是自足的——范畴里有本体，本体里就有断言。between 是「把 A 的断言翻到 B」，那 A 的断言应该从 A 读出来，但代码里是外部硬传的。理想 CLI 要么从源范畴自动导出断言，要么加一个 —assertions 参数。这是接真实 CLI 前必须先定的一项输入契约。
