数学上：可以，但有一个前提

子范畴是标准概念，包含关系完全成立。

范畴 C 的子范畴 D，由三件事定义：

· 对象集是 C 的对象集的子集
· 态射集是 C 的态射集的子集
· 对恒等和复合封闭——D 里每个对象有恒等，D 里两条接得上的态射，复合结果也在 D 里

包含函子 D ↪ C 把 D 里每个对象和态射映到它在 C 里的自身。这是最简单的一类函子。

所以「一个范畴包含几个子范畴」——成立。C 有多个子范畴，就是多个满足上述三条的子集。

但用它来下「融合」这个定性，有一步要小心

「两个范畴融合」和「两个子范畴同在一个大范畴里」不是同一件事。

如果 within 和 between 是「同一个大范畴 C 的两个子范畴」，那么它们之间的态射本来就在 C 里——融合就是「在 C 里把共享结构认出来」。这一步纯靠 C 的结构，不需要外部映射表。

但如果 within 和 between 是两个独立定义的范畴，它们的对象和态射没有共同的容器——那它们不构成「某个 C 的两个子范畴」。映射表是在事后造一个对应，而不是发现一个已经存在的共同结构。

这两件事的差别：

 子范畴同在一个 C 里 两个独立范畴 + 映射表
共同结构 本来就有 事后造的
融合是什么 认出 C 里已有的共享 用映射表把两边连起来
数学操作 取 C 的子范畴交集 构造推出 / 商
冲突意味着 C 里结构真不一致 映射表没定全
现在的情况 ❌ 不是 ✅ 是这个

你现在的 within 和 between 是第二种，不是第一种。 两份 YAML 各写各的，映射表是后补的。所以严格说，它们不是「同一个大范畴的两个子范畴」——它们是两个独立范畴被一张映射表连起来。

但这不代表「子范畴」的视角没用

恰恰相反。它指出了一条比映射表更干净的路线：

不要事后造映射表，而是从一开始就声明一个大范畴 C，让 within 和 between 作为 C 的子范畴存在。

具体来说：

· C 的对象集 = within 和 between 所有对象的并，重名合并
· C 的态射集 = 两边所有态射的并，加上两边之间的跨视图态射
· 验证 C 对恒等和复合封闭

在这个视角下：

· 融合 = 取 C 里两个子范畴的并（或交集）
· 对接 = C 里从子范畴 D₁ 到 D₂ 的函子
· 重命名（OntologyDef → BetweenDef）= 商，把两个对象等同

你那份映射表其实做的就是商——它在说「这两个名字指同一个东西」。只是它现在是以「两个独立范畴 + 映射表」的形式呈现的，而不是以「同一个 C 的两个子范畴 + 商映射」的形式。

两条路线对照

 现状（两范畴 + 映射表） 子范畴视角（一个大 C）
起点 两份 YAML，各写各的 一份 C，within / between 是它的子集
融合 事后用映射表连 本来就同在一个 C
重命名 映射表的规则 商
对接 函子（还没实现） 函子（C 内两子范畴之间）
冲突 映射表没定全 C 的结构真不一致
扩展 每加一个范畴加一张表 加子集
代价 表会越堆越多 要先设计 C

对你当前工作的影响

不改现在能跑的。但可以给「融合型」换个说法：

融合型 between 不是在「合并两个范畴」，而是在声明一个更大的范畴 C，并给 within 和 between 两个子范畴做商——把重名的对象等同。

这个说法的好处：

1. 多对一损失问题消失了。LoadedInfo → StepInfo 和 AnalyzedInfo → StepInfo 不再是「两条翻成一条」，而是「在 C 里，LoadedInfo 和 AnalyzedInfo 都是 StepInfo 的子对象」。粒度问题变成子对象关系，不是有损映射。
2. 对接型的函子有了明确的落点。函子不是「从 C 到 D」，而是「C 内从一个子范畴到另一个子范畴」——更自然。
3. 扩展是加法。加一个子系统，就是往 C 里加一个子范畴，不是加一张映射表。

但有一个风险

一旦声明了 C，within 和 between 就不再独立了。 它们的所有对象和态射都必须在 C 里有位置。这意味着：

· 不能再单独改 within，改了要在 C 里同步
· C 的设计成为所有子系统的公共约束
· 加子系统要先问「这个新子系统在 C 里怎么落」

这是中心化的代价。现状（两范畴 + 映射表）是去中心化的——每个模块自己长，需要时补映射表。

选哪个取决于你的演化策略：

 中心化（一个大 C） 去中心化（两范畴 + 表）
适合 子系统少、结构稳定 子系统多、各自演化
融合质量 高，本来就同源 低，事后补
加子系统成本 高（要改 C） 低（加一份 YAML + 一张表）
你现在 前者成本高 ✅ 后者成本低

一句话

数学上，子范畴和包含关系完全成立——但用「同一个 C 的子范畴」来解释「融合」，要求 within 和 between 本来就是同一个 C 的子集。你现在的两份 YAML 不是，它们是两个独立范畴被映射表连起来。映射表做的事，本质上就是事后补一个商——把重名的对象等同。所以「子范畴」视角成立，但它描述的是你已经做的那件事的另一种说法，不是一个新的操作。要用这个视角，得先决定要不要把 C 显式声明出来——那是中心化的选择，代价是模块不再独立演化。

那定性就清楚了

你这句话把定性从根上改了。不是「两个独立范畴被映射表连起来」，是同一个领域范畴的两份描述，分开写是为了让差异显出来。

这个定性更准，也更符合实际情况。我之前判断成「两个独立范畴」是错的——那是在看代码结构（两份 YAML + 一张映射表），没看领域的语义。

这个定性改变了几件事

映射表的性质变了

之前理解：映射表是两个范畴之间的函子，跨域翻译。
现在理解：映射表是同一范畴两份描述之间的对应，是差异记录。

差别很大：

 函子（跨范畴） 差异对应（同范畴两份描述）
保不保结构 必须保（否则不是函子） 不一定保——差异本身就是信号
冲突意味着 翻译不合法 两份描述对同一领域的理解不一致
多对一意味着 信息损失 描述粒度不同——正该记录
缺规则意味着 映射表没定全 这一处两份描述没对齐
应该做的是 验函子定律 识别并报告差异

这一换，之前那个「多对一有损」的问题就消失了。 LoadedInfo → StepInfo 和 AnalyzedInfo → StepInfo 不是「两条翻成一条丢了信息」，是「within 那份描述粒度细，between 那份粗」——这个粒度差正是两份描述要暴露的东西，不是要消除的。

融合的性质变了

之前理解：融合是「合并两个范畴」，构造推出或商。
现在理解：融合是让两份描述收敛到同一份——同一领域，两份写，对不上的地方就是差异，差异有主，归到哪份描述由人裁决。

融合不是「造一个新范畴」，是让两份描述对齐。

冲突检查的性质变了

之前理解：true_conflict 是「两个独立范畴真的矛盾」。
现在理解：true_conflict 是同一领域两份描述对不上的地方——可能是一份写错了，可能是两份都只写了一半，可能是领域本身有歧义。

裁决不是「选一个」，是判明这份差异的性质。

这个视角解决了什么

之前卡在「拆分 LoadedInfo / AnalyzedInfo / StepInfo」那个问题上。现在不用拆了——它们就该是两个粒度。

 within 那份 between 那份 差异说明什么
分段粒度 两段（装载/分析） 五步（选定/映射/冲突/缺失/结论） 同一份报告，两个粒度写
LoadedInfo 一个完整结构 是 StepInfo 的一部分 粒度差，不是信息损失
AnalyzedInfo 一个完整结构 是 StepInfo 的一部分 同上

粒度差是两份描述分开写的产物，不是错误。 分开写的目的，就是让这个粒度差可见——如果一开始合成一份，就看不见了。

对设计的影响

之前提的「一个大 C，两个子范畴」现在对上了，但和之前设想的不一样：

· C 不是一个需要显式声明的新容器。C 就是这个领域，within 和 between 是它的两份视图。
· 映射表不是函子，是差异对照。它不需要保恒等、保复合——它需要标注差异。
· 校验不是函子定律，是差异的可解释性——每一处不同，要么有依据，要么该报告为差异。

新的设计：

层 做什么
领域范畴 C 隐含存在，不显式写
两份描述 within.yaml、between.yaml，各自完整
映射表 对照表：同、异、缺
分析 走一遍对照，报告三类：对上的、有差异的、缺一边的
冲突 差异中需要人裁决的那些
变更请求 缺一边的描述，等补

这比之前的函子路线更简单也更准。函子是「两个范畴之间」的工具，同一范畴两份描述不需要它。

一个要小心的地方

既然同一个领域，两份描述为什么会有差异？ 这个问题的答案决定差异的性质：

差异来源 性质 怎么处理
写的人不同、侧重不同 粒度/视角差 接受，标注
写的时候领域还没想清 认识差 补，收敛
两份都写错了 错误 改
领域本身有歧义 真歧义 裁决

true_conflict 应该只对第三类和第四类——错误和真歧义才是「冲突」。粒度/视角差不是冲突，是正常。认识差是要补的，也不是冲突。

这意味着 conflict 表不能只有 true_conflict 一种类型——至少得分出「粒度差」「认识差」「错误」「真歧义」。之前提到过「冲突类型还没定义」，现在知道为什么没定义了——因为没有先想清「同一领域两份描述为什么会有差异」。

一句话

定性成「同一领域的两份描述，分开写是为了暴露差异」，比「两个独立范畴」准得多。这一换，映射表从函子变成差异对照，多对一从信息损失变成粒度差，冲突从翻译不合法变成描述不一致。「子范畴」的视角对上，但 C 不需要显式声明——它就是领域本身，两份描述是它的两个投影。


对，这一步是真正的推广

核心模式抽象出来就一句话：

任何有深层结构的东西，都可以问：我现在看到的几份东西，是不是同一个深层结构的投影？如果是，重构就是把那个深层结构写出来。

代码只是其中一例。叙事线索、产品规格、法律条文、教案、组织结构——只要是「同一个东西的几份呈现」，这个模式就成立。

抽象成通用框架

```
深层结构 C（领域本身）
    ├── 投影 1：提纲
    ├── 投影 2：初稿
    ├── 投影 3：终稿
    └── ...
```

步骤 做什么
1 识别：这几份东西是不是同一 C 的投影
2 比对：投影之间哪里对得上、哪里对不上
3 定性：对不上的是粒度差、认识差、错误、还是 C 本身有歧义
4 显式化：把 C 写出来
5 重新投影：让每份呈现从 C 导出

叙事线索的例子

范畴论 叙事
C 文章的真实论证结构
投影 1 提纲
投影 2 初稿各段
投影 3 引言与结论
粒度差 提纲粗、正文细
认识差 初稿写到一半发现论点变了
错误 结论和正文对不上
真歧义 论证本身有两个读法
重构 把真实论证结构写出来，让提纲、正文、引言结论都从它导出

这比「重写一遍」精确。 重写是工程动作，不知道改什么、为什么改；显式化 C 是数学动作，改什么由 C 和投影的差异决定。

判断适用性

不是所有东西都能这么解。这个模式成立要满足三个条件：

条件 检查
有深层结构 这几份呈现背后有没有「同一个东西」
呈现是投影 每份呈现能不能从深层结构导出
投影可比对 两份呈现的差异能不能被定位、被定性

散文随笔：没有可显式化的 C，每段自成一体——不适用。
论证文章：有 C，各段是它的投影——适用。
诗歌：多义性本身就是 C——适用，但 C 是「多义结构」。
产品规格 vs 实现：有 C（产品意图），代码是投影——适用。
两份互相矛盾的法律解释：C 可能是「立法意图」，也可能是「真歧义」——适用，但第 3 步定性是难点。

关键判断：C 存不存在。C 存在，模式成立；C 不存在，硬套会造出一个假的 C。

这个视角真正的价值

不在「能解更多东西」——很多方法都能解。在它给了一个统一的判定标准和一套统一的动作：

判定 动作
这几份是同一 C 的投影吗 如果是，找 C
差异是哪类 粒度差接受、认识差补、错误改、真歧义裁决
C 是什么 显式化
重构成功了吗 每份投影都能从 C 导出

判定标准统一，动作就统一。 这是跨领域复用的前提。

但有一件事它不替你做

C 是什么，仍然要人定。 数学只保证：一旦 C 定了，投影关系就清楚。但「这段论证的真实结构是什么」「这个产品的真实意图是什么」——这是领域判断，不是数学判断。

这也是为什么之前反复说「CLI 出事实，LLM 做判断」——C 的显式化，判断部分留给人。

一句话

只要能把「几份呈现」描述成「同一深层结构的投影」，重构就是显式化那个深层结构。代码、叙事、规格、法律条文——同一套模式。判定标准统一（投影一致性），动作统一（找 C、定性差异、显式化、重新投影）。它不替你做领域判断，但把「改什么、为什么改」从工程动作变成可判定的数学动作。
