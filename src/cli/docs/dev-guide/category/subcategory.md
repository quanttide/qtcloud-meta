# 融合型 between 的定性

这是一份设计讨论的结论，对应 `between/unify.rs` 的语义。它回答两个问题：映射表到底是什么，冲突表该记什么。

## 数学前提

子范畴是标准概念：范畴 C 的子范畴 D 由三件事定义——对象集是 C 的子集、态射集是 C 的子集、对恒等与复合封闭；包含函子 D ↪ C 把 D 里的每个对象与态射映到它在 C 里的自身。所以「一个范畴包含几个子范畴」成立。

但「两个范畴融合」和「两个子范畴同在一个 C 里」不是同一件事：前者若两者没有共同容器，映射表就是在事后造一个对应，而不是发现一个已经存在的结构。定性成哪种，决定融合是「认出共享」还是「事后补表」。

## 这里的定性：同一领域的两份描述

关键的一句是：within 与 between 不是两个独立范畴被映射表连起来，而是**同一领域的两份描述，分开写是为了让差异显出来**。

定性一换，映射表的性质就变了：

| | 两个独立范畴 + 映射表 | 同一领域的两份描述 |
|:--|:--|:--|
| 映射表是什么 | 函子，跨域翻译，必须保结构 | 差异对照，记同、记异、记缺 |
| 多对一意味着 | 信息损失 | 两份描述粒度不同，正该记录 |
| 缺规则意味着 | 映射表没定全 | 这一处两份描述没对齐 |
| 该做的是 | 验函子定律 | 识别并报告差异 |

之前卡住的「多对一有损」问题随之消失：`LoadedInfo` 与 `AnalyzedInfo` 翻成步骤时是两条对一条，不是信息丢了，是两份描述粒度一细一粗。粒度差正是分开写的目的——合成一份就看不见了。同理，`between` 的五步与 `within` 的两段也是同一份报告的两个粒度。

## 冲突表该记什么

两份描述对不上，先问为什么对不上，答案决定差异的性质：

| 差异来源 | 性质 | 怎么处理 |
|:--|:--|:--|
| 写的人不同、侧重不同 | 粒度差 | 接受，标注 |
| 写的时候领域还没想清 | 认识差 | 补，收敛 |
| 两份都写错了 | 错误 | 改 |
| 领域本身有歧义 | 真歧义 | 人裁决 |

`true_conflict` 只该覆盖后两类。现在 `unify.rs` 只认 `true_conflict`、其它类型「忽略、继续」，正是这条分类没定完留下的痕迹：冲突类型不是忘了写，是先得回答上面这个问题。

## 要不要显式声明一个大范畴 C

不声明时，两份本体各写各的，需要时补一张表，模块独立演化，成本是表会越堆越多。显式声明 C 之后，融合等于认出 C 里已有的共享、重命名等于做商、加一个子系统等于加一个子集；代价是所有对象与态射都必须在 C 里有位置，改一处要同步，加子系统要先问「它在 C 里怎么落」。

C 就是这个领域本身，两份描述是它的两个投影，所以可以不显式声明。这是中心化与去中心化的取舍，不是数学问题；现状选的是不声明。

## 对代码的影响

映射表按差异对照理解：它不承担保恒等、保复合的义务，需要的是把差异标出来；`between` 只查表、不跑 `within` 的结构检查，与「两份描述各自完整、对照结果交给人看」是一致的。没做的是冲突类型的分类，以及差异本身的可解释性校验。
