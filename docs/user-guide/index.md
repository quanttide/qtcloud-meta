# 用户指南

本文从使用者角度走完 qtcloud-meta 的两个基本过程：把新概念写入本体，以及在范畴之间做分析。平台的全局结构见[三层极简架构方案](../index.md)。

qtcloud-meta 全部本地运行：本体层存定义，范畴层管不同方法论的共存与切换，主数据层存实例数据。当前阶段主数据的写入流程暂缓，日常使用集中在本体写入与范畴分析两条线。

## 准备

在一台开发机上准备本地环境：SQLite 数据库、Ollama 本地模型、Turtle/OWL 本体文件与审批 Web 页面。组件选型与安装清单见[开发指南](../dev-guide/index.md)。

## 本体写入的过程

目标：让文档、对话、网页里的新概念进入本体，供后续抽取与分析复用。提交一份输入后，系统内部走完这条链路：

```
非结构化输入（文档/对话/网页）
        │
        ▼
┌───────────────────┐
│  LLM 抽取          │  从文本中抽取候选概念
│  → 候选类          │
│  → 候选属性        │
│  → 候选关系        │
│  → 附原文出处      │
└───────────────────┘
        │
        ▼
┌───────────────────┐
│  本体对齐          │  与现有本体比对：已有 → 复用
│                   │  缺失 → 候选新增；矛盾 → 冲突候选
└───────────────────┘
        │
        ▼
┌───────────────────┐
│  本体校验          │  SHACL + 一致性检查：domain/range 对不对、
│                   │  新增是否破坏现有定义
└───────────────────┘
        │
        ▼
┌───────────────────┐
│  本体变更          │  生成 change_request（draft），
│                   │  记录候选定义、对齐结果与出处
└───────────────────┘
        │
        ▼
┌───────────────────┐
│  人类确认          │  审批通过 → 写入 Turtle/OWL 本体文件，生效
│                   │  审批拒绝 → 丢弃或退回修改
│                   │  修正内容 → human_edit 记录
└───────────────────┘
```

使用者的操作只有五步：

1. 提交输入：把非结构化文本交给 LLM 知识库。
1. 等待系统完成抽取、对齐、校验与变更生成，产出一条待审批的本体变更。
1. 打开审批页面：每条请求显示候选概念、对齐结果（复用、新增或冲突）、校验结果与风险等级。
1. 做出决定：批准、拒绝或修正后批准，修正内容记入 `human_edit`。
1. 批准生效：变更写入 Turtle/OWL 本体文件，本体版本加一；拒绝则丢弃或退回修改。

审批页面不需要复杂功能，一张 `change_request` 表列出全部待审批请求，加一个简单页面即可。

### 示例

场景：一篇新文档引入了现有本体（Content、Account、Material）中没有的概念。

输入文档片段：

> 矩阵内的账号按周排期统一供稿，每篇稿件先过选题会再进入制作。

LLM 抽取的候选概念：

```json
[
  {
    "candidate_kind": "class",
    "label": "排期",
    "definition": "账号供稿的时间安排",
    "matched_existing": null,
    "confidence": 0.87,
    "source_span": "矩阵内的账号按周排期统一供稿"
  },
  {
    "candidate_kind": "class",
    "label": "选题会",
    "definition": "稿件进入制作前的评审环节",
    "matched_existing": null,
    "confidence": 0.84,
    "source_span": "每篇稿件先过选题会再进入制作"
  }
]
```

后续流程逐条走完：

1. 本体对齐：现有本体只有 Content、Account、Material，「排期」「选题会」均无对应概念，判定为候选新增，与现有定义无矛盾。
1. 本体校验：新增两个独立类，不改动现有类与属性，domain/range 引用的类都存在，通过。
1. 本体变更：`change_request` 插入一条 pending 记录，`proposed_data` 记录候选类的定义与出处。
1. 人类确认：审批人批准后候选类写入 Turtle 本体文件，本体生效；拒绝则丢弃。

## 范畴分析的过程

目标：元智能体整合不同方法论的结论时，把结论从一个范畴翻译到另一个范畴。以「实体导向」范畴下的一次流程分析为例：

1. 选定范畴：当前范畴「实体导向」，本体承诺是实体、属性、关系。
1. 映射翻译：查 `category_mapping`，发现「实体导向」→「流程导向」的函子规则：「内容」→「发布活动」，「素材」→「活动资源」，按规则把分析对象翻译到目标范畴。
1. 冲突检查：比对翻译后的断言，查 `conflict` 看是否已有人类裁决；无记录则继续，有 `true_conflict` 记录则按既往裁决处理。
1. 兜底升级：函子规则不存在时，生成一条 `change_request` 等人类定义映射，分析暂停在当前范畴。
1. 输出结论：在「流程导向」范畴下给出流程视角的分析结论，回传给元智能体。
